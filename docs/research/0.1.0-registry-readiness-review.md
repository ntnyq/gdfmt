## Applied protection and maintainer permissions

The expected REST request bodies are recorded in
[`.github/repository-protection.json`](../../.github/repository-protection.json).
This file is a reviewable configuration record, not an automatic deployment.

- `main` requires a PR, up-to-date checks and resolved conversations. All 29
  existing checks were observed successful on the reviewed `main` SHA and bound
  to GitHub Actions app `15368`; there are no invented pending check names.
  The policy includes Rust quality/MSRV/tests, five engine profiles, npm's ten
  native consumers and parity/scripts, and all seven WASM/editor host jobs.
- PR approval count is `0`; code-owner and last-push approval are not required.
  The only current collaborator is administrator `ntnyq`, so a second reviewer
  is not needed to merge a passing PR. Force pushes and deletion are disabled;
  `enforce_admins: false` deliberately retains the administrator's emergency
  bypass. Ordinary changes should use passing PRs.
- Active [Version tags ruleset 25720774](https://github.com/ntnyq/gdfmt/rules/25720774)
  restricts creation, update and deletion for `refs/tags/v*`, with no exclusions.
  Repository Admin (ID `5`) and Maintain (ID `2`) have `always` bypass; ordinary
  Write access has none. REST readback matched the policy and GraphQL returned
  the actual `admin`/`maintain` role names and `ALWAYS` modes.
- `v-recovery-*` is covered by the same maintainer exception. Do not move a
  published tag for recovery: reuse the frozen bytes and use a separate recovery
  ref when needed. The existing GitHub Release job verifies an existing tag with
  `--verify-tag`; it needs no tag-creation bypass. No Actions/app bypass was added.
  The environment, gate and registry OIDC configuration were not changed.

The `main` SHA remained unchanged after configuration. Effective API settings
were checked without a push, test tag or dispatch, so execution of a new release
or recovery is not claimed. Job/matrix changes must keep the JSON record and
live required-check names synchronized. The API semantics are documented in
[GitHub branch protection](https://docs.github.com/en/rest/branches/branch-protection#update-branch-protection)
and [repository rulesets](https://docs.github.com/en/rest/repos/rules#create-a-repository-ruleset).

## Trusted Publisher contract and limits of the audit

The source workflow uses GitHub-hosted Ubuntu runners, `environment: release`
and `id-token: write` for both registry publishers and npm recovery. Expected
settings for **each of the fifteen release units** are owner/user `ntnyq`,
repository `gdfmt`, workflow filename **`release.yml`**, environment **`release`**.
The npm workflow needs both direct `npm publish` and `npm dist-tag` permissions.
Its pinned Node **24.0.0**, npm **11.21.0**, runtime guard and scoped dist-tag
workaround remain in place; the workaround's removal criteria are not met by
this read-only audit.

The [current per-package/account review](0.1.0-trusted-publisher-review.md)
repeated configuration reads for every release unit: all eight crates.io
requests returned **403**, and all seven `npm trust list` requests returned
**E401**. npm identity/profile/access requests also returned E401, and both
available browser sessions were signed out. All eight crates publicly expose
`trustpub_only: false`, which is optional-hardening state, not proof about token
existence or revocation. No interactive login or trust mutation was attempted.
This does not mean any publisher is
missing or broken. Historical records cannot show whether a publisher has since
been removed/recreated, its current environment binding, allowed actions,
account 2FA/email state or bootstrap-token revocation.

An authenticated package owner must review all eight crate settings and all
seven npm settings, including `@gdfmt/wasm`, recording only non-secret fields.
For npm, a newly created configuration needs a first successful new-version
publication within two days; skipping existing alpha.6 bytes cannot validate it.
See [npm Trusted Publishers](https://docs.npmjs.com/trusted-publishers/) and
[npm trust list](https://docs.npmjs.com/cli/v11/commands/npm-trust).
Crates.io's [configuration-list implementation](https://github.com/rust-lang/crates.io/blob/main/src/controllers/trustpub/github_configs/list.rs)
requires authentication and crate ownership.
