# 0.1.0 formatting style and Schema review

[简体中文](../zh/research/0.1.0-style-schema-review.md)

Reviewed on 2026-10-23 against the Rust implementation at
`6c11445a329b688f27fd6693a3c6314ffeedce64` (`0.1.0-alpha.6`), with the pending
release-checklist/documentation changes in the working tree. The follow-up fixes
below were completed on the same date. This record does not validate a future
release candidate.

The current default style is retained. Both P2 findings are resolved: integer
configuration input now matches Schema acceptance, and the line-width boundary
is documented. Default values and formatter layout rules are unchanged. No P0/P1
defect was reproduced within this review's scope.

## Default style to retain

The resolved host defaults, generated Schema descriptions, public JavaScript
declarations and [configuration guide](../guide/configuration.md) agree on these
14 formatting fields and their supported values:

| Field                       | Default  | Supported values            |
| --------------------------- | -------- | --------------------------- |
| lineWidth                   | 100      | 40–320                      |
| indentStyle                 | tab      | tab / space                 |
| indentWidth                 | 4        | 1–8                         |
| lineEnding                  | lf       | lf / crlf / preserve        |
| maxBlankLines               | 2        | 0–5                         |
| finalNewline                | true     | Boolean                     |
| arrayLayout                 | auto     | auto / multiline / preserve |
| dictionaryLayout            | auto     | auto / multiline / preserve |
| enumLayout                  | auto     | auto / multiline / preserve |
| dictionarySpacing           | compact  | compact / spaced            |
| trailingCommaLayout         | auto     | auto / multiline            |
| blankLinesAroundDefinitions | preserve | preserve or integer 0–5     |
| lambdaBodyStyle             | auto     | auto / multiline            |
| inlineCommentSpacing        | 1        | Integer 1–4                 |

Keep compact dictionaries, width-driven collection layout, simple inline lambdas,
one space before suffix comments, and existing definition gaps capped by
`maxBlankLines`. Changing these defaults would alter already reviewed output;
the existing explicit options cover alternative preferences.

Retain significant punctuation and literal spellings. For example, a short array
with a trailing comma can remain `[1, 2,]`; adding/removing commas, quotes or
semicolons requires a separate equivalence contract. Preserve comments and
formatter-off/on bytes even when they prevent a preferred layout.

The pure Rust formatter's default is `LineEnding::Preserve`, while resolved host
configuration uses LF. This is already documented in
[script formatting](../reference/formatting.md). Keep the distinction explicit;
it is not an accidental cross-host mismatch. CLI, Node and WASM share
`gdfmt_config::format_request` after resolution.

## P2 resolved: integer-valued number spellings

The original mismatch was in the unsigned integer fields and
`BlankLinesAroundDefinitions::Count` in `crates/gdfmt_config/src/lib.rs`.

```json
{ "format": { "lineWidth": 100.0 } }
```

At the review baseline, the generated Schema accepted this value, but
`parse_config` rejected it as a floating point value where `u16` was expected.
`gdfmt explain-config sample.gd` exited 2. `100` succeeded; `1e2` had the same
mismatch as `100.0`.

The probe reproduced this discrepancy for `indentWidth: 4.0`, `maxBlankLines: 0.0`,
`inlineCommentSpacing: 1.0`, `blankLinesAroundDefinitions: 2.0`,
`schemaVersion: 1.0`, and `overrides[0].format.lineWidth: 100.0` as well.
The original configuration matrices did not exercise these representations.

Shared field deserialization now accepts integer-valued decimal/exponent
representations within the existing bounds. It checks integrality and the unsigned
range before conversion, then retains the target integer type's range checks and
configuration validation. Fractions, out-of-range values, strings, `null` and
unsupported schema versions are still rejected. Duplicate-key rejection and
field-path diagnostics are retained. Regression tests cover base fields,
overrides, merging, browser helpers and inherited CLI configuration. Resolved
configuration serializes normalized integers; defaults and field names are unchanged.

## P2 resolved: the documented line-width boundary

Affected code: `crates/gdfmt_formatter/src/layout.rs:537` concatenates binary,
ternary, cast and type-test expressions with spaces; member/call chains also lack
general break points. The public formatting/compatibility pages and `lineWidth`
Schema description previously mentioned indivisible tokens/types but omitted
these expressions.

At `lineWidth: 100`, this input formats to a 112-column line with no diagnostics:

```gdscript
var result = first_value + second_value + third_value + fourth_value + fifth_value + sixth_value + seventh_value
```

A six-method chain in the probe remains 118 columns. Parenthesizing the binary
expression lets the outer group break, but its inner expression still occupies
103 columns, including indentation. The same limitation reproduces at width 40.
Calls and nested collections with supported element breaks wrap successfully.

Both languages now describe `lineWidth` as a target over supported break points,
including long expressions/chains, retained comments/literals, type references
and protected regions. The Rust field documentation and regenerated Schema
description match. Regression tests lock the existing long-expression/chain
output at widths 40 and 100, including validation and idempotence. General
expression wrapping remains follow-up work; no parentheses or backslashes are
inserted to force a line to fit.

## Regression coverage and remaining scope

- `crates/gdfmt_config/tests/config.rs` compares Schema/runtime acceptance for
  integer, decimal and exponent representations at numeric bounds, with base
  fields and overrides. It checks normalized output, defaults, zero/false merging,
  invalid values, duplicate keys and field paths.
- `crates/gdfmt_config/tests/text.rs` covers direct text formatting, JSONC browser
  configuration parsing and layer resolution, including invalid inherited values.
- `crates/gdfmt_cli/tests/cli.rs` verifies inherited decimal/exponent configuration
  and overrides through `explain-config` and stdin formatting.
- `crates/gdfmt/tests/layout_boundaries.rs` verifies exact, validated and idempotent
  long-expression/chain output at both widths. Existing formatter snapshots also
  remain the default-style baseline.

The initial review passed 49 focused tests and examined 16 source samples at
widths 40 and 100. Its temporary numeric probe captured the failures above before
the fixes; the permanent regressions now cover those cases.
